# Local adapter calibration

This is a local comparative harness, not an official AltruAgent result. The public guide was fetched without credentials on 2026-10-16 from https://api.altruagent-game.com/skill/redalert. Engine sources are yxc20089/OpenRA commit `9b271c1a5562a07deeb1c3f81d9a556cd563a676`; `ObservationSerializer.cs`, `ActionHandler.cs` and the exact commit's `rl_bridge.proto` define the transport. The generated Python protobuf files were produced from that checked-out proto using grpcio-tools.

Policy input comes exclusively from the controlled seat's engine observation plus public static engine rules and map files. Enemy actors only come from `visible_enemies` and `visible_enemy_buildings`. The serializer checks the controlled player's shroud visibility. Enemy rows are reduced to id, type, cell coordinates, integer-percent HP and wreck flag; enemy power, activity, production, ownership and other enriched bridge fields are discarded. The entire spatial tensor is ignored: its global dynamic resource density is not a platform entitlement. No referee input is read or passed to a policy.

Public static data is reconstructed from the packaged MiniYaml rules, including inherited actor traits, and the three original map packages. Binary map format 1/2 uses x-major tile and resource ordering. Terrain types are mapped to ground/water/rock/tree/wall symbols, static neutral building footprints become occupied cells, mines and spawns retain separate symbols, and only initial ore/gems from the packaged map are used. All three maps resolve every terrain template without an unknown cell. Frozen evaluation map copies keep the same terrain bytes and neutral actor layout; their public starting conditions are set separately by the runner.

Known differences and limits:

- The platform is continuous real time; this harness advances the engine in requested tick intervals through direct local gRPC, without live network latency, grants, leases or server queueing. The bridge can advance an additional tick beyond the request. Reports and observations use the actual returned tick.
- The full public platform `get_game_config` snapshot was not available. Costs, base production time, power, HP, armor, speed and primary weapon name/range/damage are reconstructed from public engine files. The adapter intentionally omits weapon `reload_seconds`: actor charging and burst behavior cannot be inferred from a weapon's `ReloadDelay` alone. Existing policy weapon timing profiles remain in use. Build time is the base value without low-power or additional production-building modifiers; observed production timing comes from the engine.
- The local map picture is reconstructed rather than byte-compared with the current official platform picture. Terrain template data, initial resources, neutral actor footprints, playable bounds and spawns are public, but exact platform rendering conventions were not accessible for comparison.
- HP uses nearest integer percent, with .5 rounded upward. The official guide says percent but does not publish its exact rounding formula. For `base_center`, a surviving construction yard's observed cell is preferred; otherwise the arithmetic center of buildings, then living units, is rounded. The guide does not specify rounding or tie behavior with multiple yards.
- The bridge lacks a separate `powered_down` field. The adapter tracks its own requested power toggles, assumes a normal initially enabled state, and uses the bridge's `is_powered` for observed working power. This may differ from the platform when toggle application fails or power state depends on disabled traits.
- Events are reconstructed from consecutive own-seat observations, using observed creations/losses/HP reductions, first enemy sightings, production readiness and power transitions. They follow the last-20-event window and 10-second per-actor attack throttling. Exact engine event timestamps, `building_sold`, `wreck_id` and inferred `enemy_killed` are not supplied. A transport entry or deployment can appear as unit disappearance in this approximation.
- Orders expand one unit per bridge command and repeat `train` for its count. Explicit harvest destinations, placement preferences, attack-ground and unit stance are retained. Own-actor and visible-target checks run before conversion. A building's `repair.on` is implemented as an observed-state-aware toggle. Build/train use the engine's own production-queue search; placement uses the engine's preferred-position-then-auto-place behavior.
- This bridge supplies no faithful delayed per-command acknowledgements. The adapter reports `no_feedback`, so production/place/deploy confirmation still requires observation changes in the policy controller. Rejected engine orders are not individually distinguishable here. The retained controller statistic named `engine_ok` counts adapter submissions marked `ok/no_feedback`; it is not a count of engine-confirmed commands.
- The runner's terminal-observation patch reports the controlled player's actual `WinState`. A run that reaches its time limit without that state remains censored unless a separately documented referee is later added. It is not automatically a draw or win. Stock built-in AI may use privileged engine information.
- `--seconds` is both the game horizon shown to the policy and the stopping point. A 90-second smoke is therefore a 90-second game and may legitimately suppress economic investment; it is not a truncated first 90 seconds of a 20-minute strategy.

Validation: 11 adapter checks cover public reference costs/build times, three-map bounds and complete terrain lookup, frozen-map compatibility, spatial-data exclusion, enemy field minimization, ready queues, reconstructed event throttling, command expansion, target permissions, repair idempotence and actual policy deployment-to-power-plant startup. A real-engine smoke verified MCV deployment, power and barracks construction and infantry training. Smoke outcomes are not benchmark samples. Runs started after the reporting update record a SHA-256 of policy source files and whether those files stayed unchanged during the run. Four earlier reports (released_v24 and candidate_a, development_1 and development_2) do not have those fields; their frozen manifests and timing records are retrospective provenance, not an original in-run source fingerprint. The original reports are preserved unchanged.
